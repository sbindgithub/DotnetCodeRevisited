Singleton → Scoped ILLEGAL Runtime error: "Cannot consume scoped service from singleton". After request ends, DbContext is disposed but Singleton holds reference → crash. Make consumer Scoped, or use IServiceScopeFactory
Singleton → Transient CAUTION Allowed but Transient is resolved once during Singleton construction → becomes effectively Singleton for app lifetime. Defeats purpose of Transient. Use IServiceProvider.GetRequiredService<T>() inside method, or factory Func<T>
Singleton → Singleton SAFE Both live for app lifetime. Completely valid. Ensure thread-safety if mutable state exists. No fix needed. Ensure thread safety.
Scoped → Singleton SAFE Longer lifetime injected into shorter lifetime. Perfectly valid. Common pattern: Scoped business service injecting Singleton cache or logger. No fix needed.
Scoped → Scoped SAFE Both live per request. Shared within same HTTP request scope. Standard pattern. No fix needed.
Scoped → Transient SAFE Transient created fresh each time Scoped service requests it. Perfectly valid. No fix needed.
Transient → Singleton SAFE Singleton is long-lived; Transient is short-lived. Each Transient instance gets the same Singleton. Valid and common. No fix needed. Watch for shared mutable state in Singleton.
Transient → Scoped SAFE If within an active scope (HTTP request), valid. Transient gets the current scope's instance. Ensure Transient is only resolved within active scope context.
Transient → Transient SAFE Both get fresh instances. Completely valid. Watch performance with heavy objects. No fix needed. Monitor memory/perf for heavy objects.
Background Worker (Singleton) → DbContext (Scoped) ILLEGAL BackgroundService is Singleton. DbContext is Scoped. Direct injection fails at startup. Inject IServiceScopeFactory. Create scope per job iteration. Resolve DbContext inside scope. Dispose after.
ARCHITECT RULE
The Golden Rule
Inject equal or longer lifetime into shorter lifetime. Flow safely: Singleton → Scoped → Transient. Never reverse this.
DECISION
When to Use Singleton
Service is stateless, thread-safe, expensive to create, or represents shared infrastructure. Never hold request-specific data in Singleton.
AVOID
10+ Constructor Params
If a class needs 8+ injected dependencies, don't blame DI. Blame the design. Break responsibilities. Use Facade or Mediator patterns instead.
